# 手机1 上跑模型：实测边界

结论先写：**能跑。之前判定"不能"是因为我配错了参数，不是硬件不够。**

## 事故与纠正

第一次尝试在 phone1（Snapdragon 7+ Gen 2 / 15 GB RAM，同时跑 8 个服务）上
用 `llama-cli` 加载 qwen3-4b.gguf（2.5 GB），结果 **Android 杀掉了整个 Termux
进程组**，8 个服务全灭，SSH 断开。而且当时以为是"模型太大"。

第二次带内存轨迹记录器重做，才看清真正的原因：

| | 默认 `-c`（未设） | `-c 2048` |
|---|---|---|
| llama RSS | **9~10 GB** | **2.67 GB** |
| MemFree 最低 | 15 MB | 5807 MB |
| Swap 消耗 | 5.5 GB（耗尽到 4 MB） | 几乎为 0 |
| 服务存活 | 全灭（第一次）/ 勉强存活（第二次） | 8/8 全程正常 |

**模型文件大小从来不是约束。** 不设 `-c` 时 llama.cpp 按模型的训练上下文长度
分配 KV cache —— Qwen3 是 32k~40k，36 层算下来约 7 GB。那 7 GB 才是元凶。

## 为什么"还有 9 GB 可用"救不了它

```
MemTotal      14.93 GB
MemFree        0.76 GB   ← 真正空闲只有这么多
Cached         8.67 GB   ← 「可用」里绝大部分是页缓存
MemAvailable   9.63 GB   ← 乐观估计
SwapFree       5.45 GB   ← 平时就已用掉 1.5 GB
```

⚑ 加上进程优先级：**Termux 的 `oom_score_adj = 200`**（安卓刻度：0 前台 /
100 可见 / **200 ← Termux** / 300 备份 / 900 已缓存）。`termux-wake-lock` 和常驻
通知把它从 900 抬到 200，但 200 依然是随时可牺牲的档位。

所以当一个 adj=200 的进程一次性申请 10 GB、而 MemFree 只有 760 MB 时，
内核先丢页缓存、再压 swap、然后杀掉发起者。**可用内存不是约束，
申请速率 + 进程优先级才是。** 不 root 改不了 `oom_score_adj`。

## 第二个坑：`llama-cli` 的空转循环

`-no-cnv` 加 stdin 重定向到 `/dev/null`，**它照样进交互模式并在 EOF 上空转**：

```
378 MB 日志里，"> " 出现 499,488 次     （约 2 MB/s 写盘 + 持续烧 CPU）
```

这个和内存无关，是构建（b10290）自身行为。第一次事故很可能是
**内存压力 + 这个空转循环叠加**的结果。

**改用 `llama-completion`** —— 同一个包里就有，是非交互的一次性推理工具。
（`llama-simple` / `llama-simple-chat` 也可用。）

## 可用的做法

```bash
# 一次性推理：实测 RSS 2.67 GB，服务全程 8/8
llama-completion -m ~/nas/models/qwen3-4b.gguf -p "..." -n 96 -c 2048 -t 2
```

- `-c 2048` 不能省。这是这整份文档的要点。
- `-t 2` 留核给其他服务（设备 7 核可见）。
- **常驻 `llama-server` 要权衡**：2.67 GB 常驻会把 MemFree 从 6.3 GB 压到
  3.6 GB。问题不是这个数字太小，而是 LMK 对分配尖峰敏感 ——
  长期更薄的余量意味着下一次尖峰更容易触发杀进程。
  建议像 Grafana 一样按需启停（`services.sh` 支持单独操作）。

## 附带教训

第一次事故里**什么证据都没留下** —— SSH 会话和进程一起死了，只能事后推测，
于是推错了。第二次先起一个每秒 `echo >> file` 的记录器（不能把整个循环
重定向到文件，那样 shell 缓冲区里的最后几秒会随 SIGKILL 一起丢），
才拿到轨迹。

**在会杀掉观测者的实验里，证据必须先落盘。**

# 后记：什么才真的能杀掉它（六个实验）

上面那句「不设 `-c` 会把 Termux 搞死」是**错的**。做了六个实验才搞清楚。

## 五次假否证 —— 全都因为我在自己画的线前停下

| 实验 | 上限 | 结果 |
|---|---|---|
| 匿名内存 | `--max 14000`（14 GB） | 存活 —— 而可寻址是 **21.9 GB**，压根没撞墙 |
| CPU 4 线程 | 180 秒 | 存活（80°C，系统**降频**而非杀进程） |
| CPU + 2 MB/s 写盘 | 180 秒 | 存活 |
| mmap 8.64 GB 逐页 touch | 14 GB | 存活，RSS 9.5 GB，**不碰 swap**（文件背景页） |
| 进程数 | 60 个 | 存活 —— **phantom 上限 32 在这台 realme 上未生效** |
| 原样复现 llama（不设 -c） | 8.5 分钟 | 存活，RSS 8.59 GB，swap 归零数分钟 |

**每一个「存活」都是假否证。** 参数是我拍的，而不是设备的边界。

## 真正的阈值

`--max 30000 --hold 0.5`（超过 RAM+swap 总量，且不给内核喘息）：

```
alloc   memfree memavail swapfree cached  rss    oom_score
14336     15      456      704     671   10209   1226
15360     16      147        0     325   10525   1256
16896     51      166      105     258   11418   1302   ← 被杀
```

**约 17 GB 时被杀。判据不是「内存不够」，是「内核无处可回收」** ——
swap 剩 105 MB、页缓存剩 258 MB，两级回收同时见底才动手。

这就是为什么 llama 的 8.6~10 GB 安然无事：那时 swap 还剩 5 GB。

## 更重要的发现：杀进程 ≠ 杀应用

这次 watchdog **1 分钟内全自动恢复**（00:39:20~27 拉起 6 个服务）。
而下午那次等了 30 分钟都没恢复。两个观测都是真的，差别在于：

| | 下午 | 这次 |
|---|---|---|
| 范围 | **整个应用**（sshd 也死、全端口关闭） | 只杀子进程（**sshd 存活**）|
| JobScheduler | 被一起取消 | 仍在 |
| 恢复 | 必须有人点开 App | 全自动 |

LMK 先挑最大的那个（探针 RSS 11.4 GB）。如果那样就够了，应用本身活下来 ——
自愈链完整。下午那次一定是升级到了「杀应用」，此后没有任何自动路径。

## 结论

1. **`-c 2048` 仍然该设**（RSS 10 GB → 2.67 GB 是实测），但理由是省内存，
   不是「防止被杀」。
2. **下午那次的死因至今不明。** llama 的负载复现不出来。
3. **防御重心不该放在「避免被杀」上** —— 阈值高得难以触及，而真正致命的
   「杀应用」是外部原因触发的、不可预测。重心应是「被杀之后能回来」。
4. `.bashrc` 钩子（打开 App 即全恢复）因此是最有价值的那一层。

## 方法论

**不要在自己设的上限前停下，然后把它当成否证。** 五次「存活」全是这么来的。
边界应该由设备定义（RAM+swap 总量、文档上的硬限制），不是由我为了安全而选的参数。

# 附录：Termux 健壮性完整杀伤矩阵

系统性地试了「除内存外还有什么能杀掉 Termux」。每次都先起独立记录器
（每秒 fsync），因为应用被杀时进程和 SSH 会话一起死，证据必须先落盘。

| 攻击面 | 极限 | 能否杀掉 | 机制 |
|---|---|---|---|
| **内存** | 约 17 GB 匿名分配 | ✓ 应用级 | **两级回收见底**：swap 剩 105 MB + 页缓存剩 258 MB 才动手，不是「内存不足」 |
| **进程数** | 约 400 个 | ✓ 应用级，**最快**（几秒） | `ulimit -u`=58911，但安卓在系统层卡在 ~400。此前测 60「没事」是假否证 |
| **CPU 满载** | 8 线程 10 分钟 | ✗ 杀不掉 | 降频把温度死锁在 **80.3°C**，热杀需 95°C+，mitigation 不让它到 |
| **磁盘写** | 2 MB/s | ✗ 太慢 | 638 GB 要 88 小时才满 |
| **mmap 抖动** | 8.64 GB 逐页 touch | ✗ 杀不掉 | 文件背景页可直接丢弃，不碰 swap |

## 恢复是概率性的（关键）

三次应用级杀（sshd 也死、全端口关闭），恢复情况：

| 事件 | JobScheduler | 恢复 |
|---|---|---|
| 内存 17 GB（00:47） | 存活 | watchdog 自动，**8 分钟** |
| 进程 400（09:23） | 存活 | watchdog 自动，**<1 分钟** |
| 下午那次 | 被取消 | 30 分钟无恢复，靠人点 App |

**2/3 自动恢复。** 所以「应用被杀 → JobScheduler 必被取消」是错的 ——
存活是概率性的，取决于安卓是「内存压力杀」还是更彻底的 force-stop，
从外部区分不了。下午那次是坏运气，不是规律。

## 对无人值守的结论

1. **正常负载几乎不可能触发被杀** —— 内存要 17 GB、进程要 400、CPU 杀不掉。
   服务空载才 14 个进程、几百 MB 内存。
2. **真被杀了，2/3 概率 watchdog 自动恢复**（1~8 分钟）。
3. **剩下 1/3（应用被 force-stop）只能靠人** —— `.bashrc` 钩子（打开 App 即全恢复）
   是这一档唯一的路。
4. 折腾一整晚的净结论：**这套 shell 方案已经覆盖了能自动化的全部**，
   剩下的缺口是 root 才能补的（写 oom_score_adj / 系统级守护），
   而它们的收益（把 1/3 手动降到 0）要用一次全盘清除去换。
