> 方法沿用前面：**先量，再决定**。教程默认值一律先验证再采用。
> 环境：qwen3:14b + nomic-embed-text / bge-m3（Ollama 0.32.5），M4 Pro 24GB。

## ⚑ 先证明你需要 RAG（这一步大多数教程直接跳过）

和 Phase 1「约束解码的收益 = 基线不合规率」是同一个道理：**RAG 的收益要先算出来。**

### 整个语料能不能直接塞进上下文？

```
qwen3 默认  40,960 ctx  ->  语料占 61.9%   挤占严重
128k 上下文             ->  语料占 19.3%   ✅ 全塞得进
```

**在这个语料规模下，如果模型有 128k 上下文，RAG 的"装不下"这个理由不成立。**

### 那 RAG 到底省了什么？实测

```
只给 1 篇（完美检索）     420 token    prefill   2.3s   总  9.2s
全塞 117 篇           25,845 token   prefill 264.5s   总 272.7s
```

**prefill 差约 115 倍，答案一模一样。** 全塞要等 4.5 分钟。

### 而且成本随语料**超线性**增长 —— Phase 0 的结论在这里被验证

Phase 0 算出：每层 `二次项/线性项 = n/d`。qwen3-14B 的 `d ≈ 5120`：

| prompt token n | n/d | prefill | tok/s | 实测倍数 | 若线性应为 |
|---|---|---|---|---|---|
| 1,044 | 0.20 | 5.6s | 186 | 1.0x | 1.0x |
| 4,164 | 0.81 | 19.1s | 218 | 3.4x | 4.0x |
| 11,928 | 2.33 | 64.0s | 186 | 11.4x | 11.4x |
| 25,819 | 5.04 | 176.0s | **147** | **31.4x** | 24.7x |

`n/d < 1` 时线性项主导；`n/d` 到 5 时二次项浮现，吞吐从 186 掉到 147 tok/s，比线性多付 27%。

> **RAG 的真正收益不是「语料塞不进去」，而是「prefill 成本随语料超线性增长」。**
> 这个说法比教程里的「上下文窗口有限」准确得多，而且能定量。

⚠️ 同一个 n 两次测得 264s / 176s，波动 50%（内存压力 + 温度）。趋势可靠，绝对值别当准数。

## 切片：教程的默认值在这个语料上是灾难 ✅

把全部语料首尾相接后按 **512 token 固定切片**（教程最常见的默认值）：

```
切出 50 个 chunk
平均每个跨 3.3 个 runbook，最多 7 个
只有 4/50 的 chunk 只含单个 runbook
```

查 `KubePodCrashLooping` 召回的 chunk 里会混着 `KubePodNotReady`、`KubeContainerWaiting`。
**「512 token + 50 overlap」是为长文档设计的，而这个语料的中位文件只有 145 token。**

### 那按段落切呢？实测反驳了这条建议

| 切片模式 | chunk 数 | R@1 | R@3 | R@5 | 日文 R@3 |
|---|---|---|---|---|---|
| **whole**（一文件一 chunk） | 108 | 76% | **86%** | **90%** | 33% |
| section（按四段切） | 384 | 76% | 83% | 86% | **0%** |

**按段落切更差。** 推测原因：切细后 chunk 变短，而 384 个 chunk 里大量 `Impact` / `Meaning`
段落语义雷同（满屏 "Service degradation"、"Cluster unavailable"），互相干扰。
（已在每段前拼上文档标题，仍不够。）

> **切片策略必须按语料的实际形态定，不能照抄默认值。**
> 这个语料的正解是「一个文件一个 chunk」，因为文件本身已经是一个完整的语义单元。

## 检索评测：29 条查询，五类 ✅

测试集刻意覆盖真实场景而非理想情况（`rag/testdata/queries.json`）：

| 类型 | 条数 | 测什么 |
|---|---|---|
| A 直接告警名 | 4 | 基线，精确匹配 |
| B 英文症状描述 | 12 | 真正的语义检索（不提告警名） |
| C 中文症状描述 | 6 | **语料 100% 英文，测跨语言** |
| D 日文症状描述 | 3 | 用户在日本工作，运维记录常是日语 |
| E 近义混淆 | 4 | 精度（语料里有多组名字极近的告警） |

### 结果：英文满分，非英文崩溃

```
配置              R@1  R@3  R@5   A告警名  B英文  C中文  D日文  E近义
nomic whole       76%  86%  90%   100%   100%   67%   33%   100%
nomic section     76%  83%  86%   100%   100%   67%    0%   100%
nomic 无前缀       79%  86%  86%   100%   100%   67%   33%   100%
bge-m3 whole      86%  93% 100%   100%    92%  100%   67%   100%
```

**① 英文语义检索是满分。** B 类 12/12，**E 类近义混淆一个没错** ——
`KubeQuotaFullyUsed` / `KubeQuotaAlmostFull` / `KubeQuotaExceeded` 三个名字极近的告警
全部分对。embedding 在英文上没问题。

**② 中日文失败有规律，不是随机。** 失败的全是**磁盘/存储空间**类查询
（`节点磁盘空间快满了`、`PVC 存储空间不足`、`ノードのディスク容量が不足`），
而 `Pod 重启` / `etcd leader` / `容器 Waiting` / `CPU 限流` 全部命中 #1。
说明模型对部分中文概念有映射、对另一部分没有。

**③ nomic 任务前缀几乎无影响 —— 我的假设被否证。**
我在 `index.py` 注释里写了「漏掉 `search_document:` / `search_query:` 会掉召回」，
实测**无前缀 R@1 反而略高（79% vs 76%）**，R@3 完全相同。

⚠️ **分类型的数字必须打折看**：D 类只有 3 条，`33% vs 67%` 就是**一条查询的差别**；
C 类 6 条、E 类 4 条同理。整体 R@k（n=29）相对可信，分类型只能看方向。
（Phase 1「先量噪声再解读差异」的规矩。）

## 跨语言：两条路，且**不能叠加** ✅

| 方案 | R@1 | R@3 | R@5 | 中日文 R@3 | 单查询延迟 |
|---|---|---|---|---|---|
| nomic 直接 | 76% | 86% | 90% | 56% | **24ms** |
| **nomic + 查询翻译** | 79% | **100%** | **100%** | **100%** | 918ms |
| bge-m3 直接 | **86%** | 93% | 100% | 89% | 463ms |
| bge-m3 + 查询翻译 | 79% | 93% | 97% | 89% | 763ms |

**查询翻译**（用已有的 qwen3 把中日文查询翻成英文再检索，零新依赖）把中日文 R@3
从 56% 修到 **100%**，整体 R@3/R@5 双满分 —— 全场唯一做到的。

### 反直觉的发现：组合起来更差

`bge-m3 + 翻译` 的 R@1 是 79%，比 `bge-m3 直接` 的 86% **更低**。

> **翻译是有损的** —— 它抹掉了原文的细微差别。对本来就能处理多语言的模型，
> 翻译是降级而不是增强。**两个方案会互相干扰，不能叠加。**

### 选型结论

对 Agent 场景（取 Top-k 塞进 prompt 让模型综合），**R@3 比 R@1 重要**，
所以选 **nomic + 查询翻译**。端到端算：翻译 0.9s + Top-3 prefill ≈3.5s ≈ **4.4s**；
对比 bge-m3 直接 0.46s + Top-5 prefill ≈5.8s ≈ **6.3s**。前者还更快，且 chunk 维度更低。
